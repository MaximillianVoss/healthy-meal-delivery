# Сервис доставки готового здорового питания

Подсистема автоматизирует выбор готовых блюд и рационов, оформление заказа, планирование доставки и контроль его состояния. Клиент видит состав и пищевую ценность, оператор управляет меню и заказами, курьер отмечает этапы доставки. Это начальная структура учебного проекта: в текущей версии подготовлены документация и правила работы с репозиторием; прикладной код будет добавлен следующим этапом.

## Назначение и границы

Система рассчитана на одну службу доставки с одним часовым поясом. Основной сценарий: клиент выбирает блюда или готовый рацион → проверяет состав и аллергены → задаёт адрес и интервал → подтверждает заказ → оператор проверяет доступность → курьер передаёт заказ → статус становится «Доставлен». Изменение статуса записывается в журнал.

Меню, рацион, блюдо, состав/аллергены, заказ/позиции, адрес, интервал доставки и курьер образуют основные сущности. Стоимость фиксируется в строках заказа, чтобы последующее изменение меню не меняло уже подтверждённые суммы. Пищевые значения носят справочный характер; медицинские рекомендации не формируются.

## Планируемый стек

- C# и .NET 10 LTS, ASP.NET Core Razor Pages для веб-интерфейса и API.
- Entity Framework Core и PostgreSQL 18 для хранения данных.
- xUnit для модульных проверок, отдельные интеграционные проверки БД.
- GitHub Actions для проверок изменений, Docker/OCI для будущего развёртывания.

Версии .NET 10 и PostgreSQL 18 подтверждены официальными таблицами поддержки на 22.10.2026. При реализации следует брать актуальные исправления выбранной поддерживаемой ветви: [политика .NET](https://dotnet.microsoft.com/en-us/platform/support/policy/dotnet-core), [политика PostgreSQL](https://www.postgresql.org/support/versioning/).

## Будущее развёртывание

1. После появления прикладного решения установить .NET 10 SDK, контейнерный runtime и PostgreSQL 18. Версии пакетов зафиксировать в lock-файле, обновления проверять отдельно.
2. Создать отдельного пользователя БД и базу healthy_meals с минимальными правами. Пароль и строку подключения передавать через секреты окружения или хранилище развёртывания.
3. Скопировать перечень параметров из .env.example в среду запуска; действующие секреты в Git не добавлять. Файл примера не содержит рабочего пароля и сам по себе не запускает систему.
4. Выполнить восстановление зависимостей, сборку и тесты; миграции применять после резервной копии. Точные команды добавляются в deploy/README.md одновременно с первым рабочим приложением.
5. Настроить HTTPS, домен, ограниченный доступ к администрированию, резервное копирование и журналирование без персональных данных и токенов. Проверить оформление заказа и восстановление БД на тестовом стенде.

Текущая проверка документации выполняется командой `python scripts/validate_structure.py`. Сборка приложения в этой версии не заявляется.

## Работа с изменениями

Основная ветвь main; рабочие ветки `feature/<описание>` и `fix/<описание>`. Изменения проходят Pull Request с описанием причины, проверки и влияния на данные. Правила защиты и параметры настройки описаны в [docs/BRANCH_PROTECTION.md](docs/BRANCH_PROTECTION.md). В локальном комплекте эти правила подготовлены; применение на GitHub требует опубликованного репозитория.

В публичный репозиторий не включаются отчёты с ФИО/группой, реальные адреса, телефонные номера, платежные реквизиты и секреты. Для разработки используются вымышленные данные. Сведения об уязвимостях не публикуют в открытых Issue вместе с ключами или личными данными.
